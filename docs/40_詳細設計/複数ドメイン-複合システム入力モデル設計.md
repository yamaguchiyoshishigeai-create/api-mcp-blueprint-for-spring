## 2. 現状整理

### 2.1 APIM for Spring の現在位置

APIM for Spring は、業務要件から Spring REST API 設計と MCP 設計を生成する設計支援Webツールである。

現時点のMVPは、自由文をAIで意味解析するシステムではなく、構造化入力UIで選択された業務ドメイン、利用者、操作種別、AI許可操作、承認必須操作、監査ログ対象などをもとに、API/MCP設計候補を静的ルールベースで組み立てる。

## 3. 問題認識

### 3.1 UIは複数ドメイン対応に先行している

TSK-021により、UI上ではカテゴリ別ドメイン候補を複数選択し、`targetDomain` へ ` / ` 区切りで反映できるようになった。

しかし、内部モデルである `BlueprintInput` は、まだ `targetDomain` を単一文字列として保持している。

そのため、たとえば以下の入力は、UI上は複数ドメインに見えるが、Generator側では長い単一ドメイン文字列として扱われる可能性がある。

    注文管理 / 商品管理 / 在庫管理

### 3.2 対象システム種別プリセットが不足している

現行の対象システム種別プリセットは4種類であり、複合業務システムの発想支援として不足している。

また、単一select形式であるため、複数システム種別を内包する統合システムを自然に表現できない。

### 3.3 対象ドメインプリセットとカテゴリ別ドメイン候補が重複している

対象ドメインプリセットは、単一ドメインを選んで対象ドメイン欄へ反映するだけである。

現在はカテゴリ別ドメイン候補を直接チェックすれば同等の操作ができるため、対象ドメインプリセットは入力正本としての意味が薄い。

### 3.4 カテゴリ別ドメイン候補の視認性が不足している

カテゴリ別ドメイン候補は存在するが、UI上はカテゴリごとのnodeまたはカードとして明確に分離されていない。

候補数が増えるほど、どのドメインがどのカテゴリに属しているかを直感的に把握しにくくなる。

## 4. 現行結論

### 4.1 先にUI整備を行う

以前は、`BlueprintInput` に `systemName`、`primaryDomain`、`relatedDomains` を追加する案を最初の後続実装としていた。

しかし現状では、UIが複数ドメイン対応に先行しており、ユーザーが直接触る入力体験側に以下の課題がある。

1. 対象システム種別候補が少ない。
2. 対象システム種別が単一選択しかできない。
3. 対象ドメインプリセットとカテゴリ別ドメイン候補が重複している。
4. カテゴリ別ドメイン候補の見た目上のまとまりが弱い。

したがって、直近では内部モデル拡張よりも、まずUI入力構造の整理を優先する。

### 4.2 UI整備後に内部モデルを再評価する

TSK-025〜TSK-027でUI入力構造を整理した後、実際の入力値の形に合わせて `BlueprintInput`、正規化処理、Generator拡張の課題を再整理する。

このため、旧案の `TSK-022-A`、`TSK-022-B`、`TSK-022-C` のような枝番運用は採用しない。

正規課題IDは `TSK-###` のみを使用する。

## 5. 推奨UI構造

### 5.1 対象システム種別プリセット

対象システム種別プリセットは、単一selectではなく、複数選択可能なチェックボックスまたはカード型UIへ変更する。

初期候補は最低10種類とする。

| システム種別 | 推奨ドメイン候補 |
|---|---|
| 社内申請ポータル | 経費精算、休暇申請、承認ワークフロー、通知管理、社員情報管理 |
| EC / 販売管理 | 注文管理、商品管理、在庫管理、請求管理、決済管理、配送管理 |
| 保守サポート管理 | 問い合わせ管理、修理依頼、FAQ管理、ナレッジ検索・要約、顧客管理 |
| ナレッジ活用基盤 | 文書管理、FAQ管理、ナレッジ検索・要約、議事録管理 |
| 人事労務管理 | 社員情報管理、組織管理、勤怠管理、休暇申請 |
| 契約・請求管理 | 契約管理、請求管理、決済管理、承認ワークフロー、監査ログ管理 |
| 開発・運用管理 | 開発タスク管理、障害管理、リリース管理、通知管理 |
| 顧客対応CRM | 顧客管理、問い合わせ管理、通知管理、ナレッジ検索・要約 |
| 資産・備品管理 | 備品貸出管理、在庫管理、監査ログ管理、承認ワークフロー |
| 統制・監査管理 | 権限管理、監査ログ管理、承認ワークフロー、契約管理 |

複数の対象システム種別が選択された場合は、各システム種別に紐づく推奨ドメインを合成し、カテゴリ別ドメイン候補へ自動チェックを入れる。

### 5.2 対象ドメインプリセット

対象ドメインプリセットの単一selectは、カテゴリ別ドメイン候補と機能が重複するため整理対象とする。

現時点の推奨は、対象ドメインプリセットを廃止または非表示化し、ドメイン選択の正本をカテゴリ別ドメイン候補へ統合することである。

対象ドメイン欄は、以下の目的で残す。

| 用途 | 内容 |
|---|---|
| 後方互換 | 既存 `BlueprintInput.targetDomain` を維持する |
| 確認 | 選択されたドメイン群を ` / ` 区切りで確認できる |
| 手動補正 | 候補にないドメイン名を一時的に補足できる |

### 5.3 カテゴリ別ドメイン候補

カテゴリ別ドメイン候補は、カテゴリごとのnodeまたはカードとして視覚的に分離する。

推奨構造は以下である。

    [人事・総務]
      □ 社員情報管理  □ 組織管理  □ 勤怠管理
      □ 経費精算      □ 休暇申請  □ 備品貸出管理

    [販売・EC]
      □ 顧客管理      □ 注文管理  □ 商品管理
      □ 在庫管理      □ 請求管理  □ 決済管理  □ 配送管理

    [承認・統制]
      □ 承認ワークフロー  □ 通知管理  □ 権限管理
      □ 監査ログ管理      □ 契約管理

各カテゴリは、`fieldset` または `.domain-category-card` のような単位で分離する。

既存の `data-target="domainCatalog"` 構造は維持し、既存の `syncSelectedDomainsToTarget()` を壊さない。

### 5.4 対象ドメイン欄

対象ドメイン欄は当面残す。

ただし、入力の正本はカテゴリ別ドメイン候補と対象システム種別プリセットとし、対象ドメイン欄は確認・後方互換・手動補正用として扱う。

## 6. 入力同期ルール

| 操作 | 期待動作 |
|---|---|
| 対象システム種別を1つ選択 | 該当システム種別の推奨ドメインへ自動チェックを入れる |
| 対象システム種別を複数選択 | 選択された全システム種別の推奨ドメインを合成して自動チェックを入れる |
| 対象システム種別の選択解除 | 該当システム由来の推奨ドメインをどう扱うかは実装時に定義する。初期案は「自動解除せず、ユーザー調整を尊重する」 |
| ドメイン候補を手動チェック | 対象ドメイン欄へ ` / ` 区切りで反映する |
| ドメイン候補を手動解除 | 対象ドメイン欄から該当ドメインを除外する |
| 対象ドメイン欄を直接編集 | 後方互換・手動補正として許容する |
| サンプル入力 | 複数システム種別・複数ドメインUIと矛盾しない状態を投入する |
| フォーム送信 | 既存hidden textarea群への集約処理を維持する |

## 7. BlueprintInputへの影響

### 7.1 直近では変更しない

TSK-025〜TSK-027では、`BlueprintInput` のフィールド追加は行わない。

理由は、まずUI入力構造を整理し、ユーザー操作としてどの入力を正本にするかを確定する必要があるためである。

### 7.2 後続で検討する候補

UI整備後、以下のようなフィールド追加を再検討する。

| フィールド候補 | 説明 | 初期優先度 |
|---|---|---:|
| `systemTypes` | 複数選択された対象システム種別 | High |
| `primaryDomain` | 主ドメイン | High |
| `relatedDomains` | 関連ドメイン群 | High |
| `targetDomain` | 後方互換用の派生値 | 既存維持 |
| `systemName` | 対象システム全体名 | Medium |
| `integrationStyle` | ドメイン間・外部連携方式 | Low |
| `architectureStyle` | 配置方式 | Low |
| `externalSystems` | 外部システム連携候補 | Low |

### 7.3 `systemName` の扱い

`systemName` は有用だが、直近の最優先ではない。

現時点では、対象システム種別の複数選択とドメイン候補の自動チェックが先であり、`systemName` は後続で追加する。

## 8. 正規化処理への影響

UI整備後、Generatorへ渡す前に入力を正規化する内部モデルを導入する。

候補名は `NormalizedBlueprintInput` とする。

役割は以下である。

| 役割 | 内容 |
|---|---|
| 旧入力互換 | `targetDomain` のみの入力を扱えるようにする |
| 新入力優先 | `systemTypes`、`primaryDomain`、`relatedDomains` があれば優先する |
| 派生値生成 | `targetDomain` を主ドメイン + 関連ドメインから生成できるようにする |
| Generator隔離 | Generator側へ互換処理を散らさない |

初期案:

    public record NormalizedBlueprintInput(
        List<String> systemTypes,
        String primaryDomain,
        List<String> relatedDomains,
        List<String> allDomains,
        String targetDomainText,
        BlueprintInput originalInput
    ) {
    }

## 9. Generatorへの影響

### 9.1 直近では変更しない

TSK-025〜TSK-027では、Generator変更は行わない。

対象システム種別プリセットとドメイン候補UIを整理しても、内部処理は当面 `targetDomain` を通じた既存生成を維持する。

### 9.2 後続での拡張方針

Generator拡張は、正規化処理導入後に段階的に実施する。

| 領域 | 拡張方針 |
|---|---|
| API設計生成 | 主ドメインAPIと関連ドメイン参照APIを分ける |
| MCP tools | 主ドメインtool、関連ドメインtool、横断toolを分ける |
| MCP resources | 主ドメインresource、関連resource、横断resourceを分ける |
| Controller候補 | 過大Controllerを避け、ドメイン別Controller候補を生成する |
| DTO候補 | ドメイン別DTO候補を生成する |

## 10. Markdown出力・AI実装指示書への影響

Markdown設計書とAI実装指示書の複数ドメイン対応は、Generator拡張より前に小さく始められる。

初期対応としては、以下を追加する案がある。

| 出力 | 初期追加候補 |
|---|---|
| Markdown設計書 | 対象システム種別、主ドメイン、関連ドメインの入力サマリー |
| AI実装指示書 | 主ドメインと関連ドメインの実装境界に関する注意 |

ただし、TSK-025〜TSK-027では実施しない。

## 12. 実装順序の推奨

現時点の推奨順序は以下である。

1. TSK-025: 対象システム種別プリセットを複数選択UIへ拡張する。
2. TSK-026: 対象ドメインプリセットを整理しカテゴリ別ドメイン候補へ統合する。
3. TSK-027: カテゴリ別ドメイン候補をnode表示へ整理する。
4. UI改善結果を確認する。
5. 本書を必要に応じて再更新する。
6. `BlueprintInput` と正規化処理の後続課題を登録する。
7. Generator / Markdown / AI実装指示書の複数ドメイン対応へ進む。

TSK-025〜027はすべてUI中心の作業であり、アプリケーションの入力モデルやGeneratorを大きく変えない。

これにより、ユーザーが見ている入力体験を先に整えたうえで、内部モデルと生成ロジックを安全に追従させる。

## 14. 結論

APIM for Spring の複数ドメイン・複合システム対応は、現時点ではUI入力支援が先行している。

ただし、対象システム種別プリセット、対象ドメインプリセット、カテゴリ別ドメイン候補のUIには整理すべき課題が残っている。

そのため、直近では `BlueprintInput` やGeneratorを先に拡張するのではなく、TSK-025〜TSK-027としてUI入力構造を整理する。

UI改善完了後、実際の入力構造をもとに、`BlueprintInput`、`NormalizedBlueprintInput`、Generator、Markdown設計書、AI実装指示書への拡張を改めて正規TSKとして登録する。

この段階的な進め方により、画面上の入力体験、内部モデル、生成ロジックの不整合を最小化しながら、単一ドメイン設計支援から複合業務システム設計支援へ拡張する。
