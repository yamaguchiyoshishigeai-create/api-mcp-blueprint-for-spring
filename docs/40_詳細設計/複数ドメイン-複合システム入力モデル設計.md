## 2. 現状整理

### 2.1 APIM for Spring の現在位置

APIM for Spring は、業務要件から Spring REST API 設計と MCP 設計を生成する設計支援Webツールである。

現時点のMVPは、自由文をAIで意味解析するシステムではなく、構造化入力UIで選択された業務ドメイン、利用者、操作種別、AI許可操作、承認必須操作、監査ログ対象などをもとに、API/MCP設計候補を静的ルールベースで組み立てる。

TSK-025〜TSK-027の完了により、入力UIは複数システム種別・複数ドメイン選択を支援する段階へ進んだ。一方、内部モデルとGeneratorは当面 `targetDomain` を中心とする既存互換構造を維持している。

## 3. 問題認識

### 3.1 UIは複数ドメイン対応に先行している

TSK-025〜TSK-027により、UI上では複数の対象システム種別とカテゴリ別ドメイン候補を選択できるようになった。

しかし、内部モデルである `BlueprintInput` は、まだ `targetDomain` を単一文字列として保持している。

そのため、たとえば以下の入力は、UI上は複数ドメインに見えるが、Generator側では長い単一ドメイン文字列として扱われる可能性がある。

    注文管理 / 商品管理 / 在庫管理

この状態は後方互換としては有効だが、主ドメイン・関連ドメイン・横断ドメインの設計境界を出力するには不十分である。

### 3.2 UI正本と内部モデルの粒度が一致していない

現在の入力正本は、画面上では以下に寄っている。

1. 対象システム種別の複数選択
2. カテゴリ別ドメイン候補の複数選択
3. 対象ドメイン欄への ` / ` 区切り反映

一方、サーバー側では `BlueprintInput.targetDomain` を中心に扱うため、次の情報を構造化して保持できていない。

- 選択されたシステム種別群
- 主ドメイン
- 関連ドメイン群
- 全ドメイン一覧
- UI選択由来か手動補正由来か

### 3.3 Generatorへ互換処理を散らすリスク

今後、API Generator、MCP Generator、Markdown Generator、AI実装指示書 Generator が個別に `targetDomain` の ` / ` 区切りを解釈し始めると、互換処理が散在し、生成品質と保守性が下がる。

このため、Generator拡張前に正規化レイヤを導入し、旧入力と新入力を一元的に解釈する必要がある。

## 4. 現行結論

### 4.1 UI整備は完了済みとして扱う

TSK-025〜TSK-027により、直近で予定していたUI入力構造の整理は完了済みである。

| 完了タスク | 内容 | 状態 |
|---|---|---|
| TSK-025 | 対象システム種別プリセットを複数選択UIへ拡張する | 解決済み |
| TSK-026 | 対象ドメインプリセットを整理しカテゴリ別ドメイン候補へ統合する | 解決済み |
| TSK-027 | カテゴリ別ドメイン候補をnode表示へ整理する | 解決済み |

したがって、次フェーズでは `BlueprintInput`、正規化処理、Generator、Markdown設計書、AI実装指示書の複数ドメイン対応へ進む。

### 4.2 後続作業は段階的に分割する

複数ドメイン対応は、入力モデル、正規化処理、API生成、MCP生成、Markdown出力、AI実装指示書に横断影響する。

そのため、1つの巨大タスクとして扱わず、以下の順序で分割する。

1. `BlueprintInput` の複数システム・複数ドメイン構造化
2. `NormalizedBlueprintInput` 導入と生成サービスの正規化経由化
3. Markdown設計書・AI実装指示書へのドメイン境界表示
4. API Generatorの複数ドメイン対応
5. MCP Generatorの複数ドメイン対応

### 5.1 対象システム種別プリセット

対象システム種別プリセットは、TSK-025で複数選択可能なUIへ拡張済みである。

初期候補は以下の10種類である。

| システム種別 | 推奨ドメイン候補 |
|---|---|

| EC / 販売管理 | 注文管理、商品管理、在庫管理、請求管理、決済管理、配送管理 |
| 保守サポート管理 | 問い合わせ管理、修理依頼、FAQ管理、ナレッジ検索・要約、顧客管理 |
| ナレッジ活用基盤 | 文書管理、FAQ管理、ナレッジ検索・要約、議事録管理 |
| 人事労務管理 | 社員情報管理、組織管理、勤怠管理、休暇申請 |
| 契約・請求管理 | 契約管理、請求管理、決済管理、承認ワークフロー、監査ログ管理 |
| 開発・運用管理 | 開発タスク管理、障害管理、リリース管理、通知管理 |
| 顧客対応CRM | 顧客管理、問い合わせ管理、通知管理、ナレッジ検索・要約 |

| 統制・監査管理 | 権限管理、監査ログ管理、承認ワークフロー、契約管理 |

複数の対象システム種別が選択された場合は、各システム種別に紐づく推奨ドメインを合成し、カテゴリ別ドメイン候補へ自動チェックを入れる。

### 5.2 対象ドメイン欄

対象ドメインプリセットの単一selectは、TSK-026で整理され、ドメイン選択の正本はカテゴリ別ドメイン候補へ統合された。

対象ドメイン欄は、以下の目的で残す。

| 用途 | 内容 |
|---|---|
| 後方互換 | 既存 `BlueprintInput.targetDomain` を維持する |
| 確認 | 選択されたドメイン群を ` / ` 区切りで確認できる |
| 手動補正 | 候補にないドメイン名を一時的に補足できる |

### 5.3 カテゴリ別ドメイン候補

カテゴリ別ドメイン候補は、TSK-027でカテゴリごとのnode/card表示へ整理済みである。

各カテゴリは `.domain-category-card` のような単位で視覚的に分離し、既存の `data-target="domainCatalog"` 構造と対象ドメイン欄への自動反映処理を維持する。

## 6. 入力同期ルール

| 操作 | 期待動作 |
|---|---|
| 対象システム種別を1つ選択 | 該当システム種別の推奨ドメインへ自動チェックを入れる |
| 対象システム種別を複数選択 | 選択された全システム種別の推奨ドメインを合成して自動チェックを入れる |
| 対象システム種別の選択解除 | 初期方針は「自動解除せず、ユーザー調整を尊重する」 |
| ドメイン候補を手動チェック | 対象ドメイン欄へ ` / ` 区切りで反映する |
| ドメイン候補を手動解除 | 対象ドメイン欄から該当ドメインを除外する |
| 対象ドメイン欄を直接編集 | 後方互換・手動補正として許容する |
| サンプル入力 | 複数システム種別・複数ドメインUIと矛盾しない状態を投入する |
| フォーム送信 | 既存hidden textarea群への集約処理を維持する |

## 7. BlueprintInputへの影響

### 7.1 後続対応方針

TSK-030では、`BlueprintInput` に複数システム・複数ドメイン入力を表すフィールドを追加する。

候補は以下である。

| フィールド候補 | 説明 | 初期優先度 |
|---|---|---:|
| `systemTypes` | 複数選択された対象システム種別 | High |
| `primaryDomain` | 主ドメイン | High |
| `relatedDomains` | 関連ドメイン群 | High |
| `targetDomain` | 後方互換用の派生値 | 既存維持 |
| `systemName` | 対象システム全体名 | Medium |
| `integrationStyle` | ドメイン間・外部連携方式 | Low |
| `architectureStyle` | 配置方式 | Low |
| `externalSystems` | 外部システム連携候補 | Low |

### 7.2 `targetDomain` の扱い

`targetDomain` は、既存Generatorと既存画面との後方互換のため維持する。

ただし、後続では `primaryDomain` と `relatedDomains` から派生可能な表示用・互換用フィールドとして位置づける。

## 8. 正規化処理への影響

TSK-031では、Generatorへ渡す前に入力を正規化する内部モデルを導入する。

候補名は `NormalizedBlueprintInput` とする。

役割は以下である。

| 役割 | 内容 |
|---|---|
| 旧入力互換 | `targetDomain` のみの入力を扱えるようにする |
| 新入力優先 | `systemTypes`、`primaryDomain`、`relatedDomains` があれば優先する |
| 派生値生成 | `targetDomain` を主ドメイン + 関連ドメインから生成できるようにする |
| Generator隔離 | Generator側へ互換処理を散らさない |

初期案:

    public record NormalizedBlueprintInput(
        List<String> systemTypes,
        String primaryDomain,
        List<String> relatedDomains,
        List<String> allDomains,
        String targetDomainText,
        BlueprintInput originalInput
    ) {
    }

## 9. Generatorへの影響

### 9.1 拡張順序

Generator拡張は、正規化処理導入後に段階的に実施する。

| 領域 | 拡張方針 | 対応予定 |
|---|---|---|
| Markdown出力 | 対象システム種別、主ドメイン、関連ドメインの入力サマリーを表示する | TSK-032 |
| AI実装指示書 | 主ドメインと関連ドメインの実装境界に関する注意を表示する | TSK-032 |
| API設計生成 | 主ドメインAPIと関連ドメイン参照APIを分ける | TSK-033 |
| MCP tools | 主ドメインtool、関連ドメインtool、横断toolを分ける | TSK-034 |
| MCP resources | 主ドメインresource、関連resource、横断resourceを分ける | TSK-034 |
| Controller候補 | 過大Controllerを避け、ドメイン別Controller候補を生成する | TSK-033 |
| DTO候補 | ドメイン別DTO候補を生成する | TSK-033 |

### 9.2 段階分割の理由

API GeneratorとMCP Generatorを同時に拡張すると、生成ロジック、テスト、期待Markdown、AI実装指示書が同時に大きく変わる。

そのため、先に正規化入力と出力サマリーを安定させ、その後にAPI側、MCP側の順でGeneratorを拡張する。

## 10. Markdown出力・AI実装指示書への影響

Markdown設計書とAI実装指示書の複数ドメイン対応は、Generator拡張より前に小さく始める。

TSK-032では、少なくとも以下を追加する。

| 出力 | 初期追加候補 |
|---|---|
| Markdown設計書 | 対象システム種別、主ドメイン、関連ドメインの入力サマリー |
| AI実装指示書 | 主ドメインと関連ドメインの実装境界に関する注意 |

この段階では、API候補・MCP候補の完全なドメイン別分解までは行わない。

## 14. 結論

APIM for Spring の複数ドメイン・複合システム対応は、UI入力支援フェーズを完了し、内部モデル・正規化処理・Generator拡張フェーズへ進む段階に入った。

次に着手すべきは、`BlueprintInput` の複数システム・複数ドメイン構造化である。

その後、`NormalizedBlueprintInput` を導入し、Generatorへ旧入力互換処理を散らさずに、Markdown設計書、AI実装指示書、API Generator、MCP Generatorを順に拡張する。

この段階的な進め方により、画面上の入力体験、内部モデル、生成ロジックの不整合を最小化しながら、単一ドメイン設計支援から複合業務システム設計支援へ拡張する。
