# TSK-022 複数ドメイン・複合システム入力モデル設計

## 1. 文書概要

| 項目 | 内容 |
|---|---|
| 文書ID | TSK-022 |
| 文書名 | 複数ドメイン・複合システム入力モデル設計 |
| 対象タスク | TSK-022 複数ドメイン・複合システム入力モデルを設計する |
| 位置づけ | 詳細設計 / 後続実装前の影響整理 |
| 主担当 | ChatGPT(リポジトリ編集) |
| 後続実装候補 | Codex |

本書は、APIM for Spring が複数ドメイン・複合システムを扱うための入力モデル、UI、Generator、Markdown出力、AI実装指示書への影響を整理する設計方針書である。

本タスクでは、大規模実装には踏み込まず、後続実装を安全に分割するための設計境界を定義する。

---

## 2. 背景と課題

現行の `BlueprintInput` は `targetDomain` を単一文字列として保持している。

TSK-021により、UI上ではカテゴリ別ドメイン候補を複数選択し、`targetDomain` へ ` / ` 区切りで反映できるようになった。しかし、内部モデルとGeneratorの前提はまだ単一ドメイン寄りである。

この状態で、たとえば以下のような入力を受け取ると、Generatorは複数の業務境界ではなく、長い単一ドメイン名として扱う可能性がある。

```text
注文管理 / 商品管理 / 在庫管理
```

その結果、以下の問題が起きる。

| 問題 | 内容 |
|---|---|
| ドメイン境界の喪失 | 注文、商品、在庫の責務分割が表現できない |
| Controller候補の粗さ | `OrderProductInventoryController` のような過大Controllerになりやすい |
| DTO候補の混在 | 異なる業務データのDTO候補が一体化しやすい |
| MCP toolの過剰集約 | AIが扱うtool境界が曖昧になる |
| 承認・監査ログ設計の粗さ | ドメインごとの危険操作や監査対象を分離しにくい |

---

## 3. 設計目標

TSK-022では、以下を満たす複数ドメイン入力モデルを目標とする。

1. 主ドメインと関連ドメインを区別できる。
2. システム全体名と業務ドメイン名を分離できる。
3. 複数ドメインをController、DTO、API、MCP toolの境界へ反映できる。
4. UIでは複雑すぎない入力体験を維持する。
5. 既存MVPの `targetDomain` 互換性を急に破壊しない。
6. 後続実装を小さなPRに分割できる。

---

## 4. 用語定義

| 用語 | 定義 | 例 |
|---|---|---|
| 対象システム名 | 生成対象となるシステム全体の名前 | 社内申請ポータル、EC販売管理 |
| システム種別 | 入力支援用のプリセット分類 | 社内申請ポータル、保守サポート管理 |
| 主ドメイン | 設計生成の中心となる業務ドメイン | 注文管理、経費精算 |
| 関連ドメイン | 主ドメインと連携する補助・周辺ドメイン | 商品管理、在庫管理、通知管理 |
| ドメイン群 | 主ドメインと関連ドメインを合わせた集合 | 注文管理 + 商品管理 + 在庫管理 |
| 連携方式 | ドメイン間または外部システムとの接続方針 | 同一アプリ内連携、外部API連携 |
| 配置方式 | 実装上の分割粒度 | モジュラーモノリス、マイクロサービス |

## 5. 推奨入力モデル

### 5.1 段階的拡張方針

既存MVPとの互換性を保つため、`targetDomain` は当面残す。

ただし、後続実装では `targetDomain` を単一正本ではなく、表示・後方互換用の派生値として扱い、内部処理では以下の構造化項目を優先する。

| フィールド候補 | 型候補 | 必須 | 説明 |
|---|---|---:|---|
| `systemName` | String | 任意 | 対象システム全体の名前 |
| `systemType` | String | 任意 | システム種別プリセット |
| `primaryDomain` | String | 必須 | 主ドメイン |
| `relatedDomains` | String | 任意 | 関連ドメイン群。改行またはカンマ区切り |
| `targetDomain` | String | 必須 | 後方互換用。主ドメイン + 関連ドメインから生成可能 |
| `integrationStyle` | String | 任意 | ドメイン間・外部連携方式 |
| `architectureStyle` | String | 任意 | モジュラーモノリス等の配置方式 |
| `externalSystems` | String | 任意 | 外部システム連携候補 |

### 5.2 初期実装での最小モデル

一度にすべて実装しない。

最小実装では、次の3項目のみを追加する案を推奨する。

| 優先 | フィールド | 理由 |
|---:|---|---|
| 1 | `primaryDomain` | Generatorの中心ドメインを明確化するため |
| 2 | `relatedDomains` | 複数ドメインを長い単一文字列から分離するため |
| 3 | `systemName` | システム全体名と業務ドメイン名を分けるため |

`integrationStyle`、`architectureStyle`、`externalSystems` は、UIが重くなるため、後続PRで追加する。

## 6. UI影響

### 6.1 現行UI

現行UIは以下を持つ。

- 対象システム種別プリセット
- 対象ドメインプリセット
- カテゴリ別ドメイン候補
- 対象ドメインテキスト欄

TSK-021時点では、カテゴリ別ドメイン候補の複数選択結果を `targetDomain` に反映している。

### 6.2 推奨UI変更

後続実装では、以下のUI構造へ移行する。

| UI項目 | UI部品 | 方針 |
|---|---|---|
| 対象システム名 | input text | 任意。未入力時は主ドメインから補完 |
| 主ドメイン | selectまたはradio | 1つだけ選ぶ |
| 関連ドメイン | checkbox群 | 複数選択可 |
| 対象ドメイン | input text | 後方互換表示。自動生成後に編集可 |

### 6.3 UI同期ルール

| 操作 | 期待動作 |
|---|---|
| 対象システム種別プリセット選択 | 主ドメイン、関連ドメイン、対象ドメインを自動投入する |
| 対象ドメインプリセット選択 | 主ドメインへ反映する |
| カテゴリ別ドメイン候補変更 | 主ドメイン未設定なら最初の選択値を主ドメイン候補にする |
| 主ドメイン変更 | `targetDomain` の先頭に反映する |
| 関連ドメイン変更 | `targetDomain` の後続へ ` / ` 区切りで反映する |

## 7. BlueprintInput影響

### 7.1 追加候補

`BlueprintInput` には以下を追加する。

```java
@Size(max = 100)
private String systemName;

@Size(max = 100)
private String systemType;

@NotBlank
@Size(max = 100)
private String primaryDomain;

@Size(max = 2000)
private String relatedDomains;
```

### 7.2 互換性方針

| 入力状態 | Generatorでの扱い |
|---|---|
| `primaryDomain` がある | `primaryDomain` を中心ドメインとして扱う |
| `primaryDomain` が空で `targetDomain` がある | `targetDomain` の先頭要素を主ドメイン候補として補完する |
| `relatedDomains` が空で `targetDomain` に `/` がある | `targetDomain` の2要素目以降を関連ドメイン候補として補完する |
| 旧入力のみ | 従来どおり単一ドメインとして処理する |

### 7.3 NormalizedInput導入案

Generatorへ直接 `BlueprintInput` を渡し続けると互換処理が分散する。

後続実装では、以下のような内部正規化モデルを導入する案を推奨する。

```java
public record NormalizedBlueprintInput(
    String systemName,
    String systemType,
    String primaryDomain,
    List<String> relatedDomains,
    List<String> allDomains,
    BlueprintInput originalInput
) {
}
```

## 8. Generator影響

### 8.1 API設計生成

API候補生成では、主ドメインと関連ドメインを分けて扱う。

| 対象 | 生成方針 |
|---|---|
| 主ドメイン | 詳細なCRUD、承認、監査ログ、Controller雛形の中心対象にする |
| 関連ドメイン | 参照API、連携API、補助Controller候補を生成する |
| 共通ドメイン | 通知、承認、監査ログなどは横断関心として扱う |

例:

| 入力 | 生成方針 |
|---|---|
| 主ドメイン: 注文管理 | `OrderController` を中心に生成 |
| 関連: 商品管理 | 商品参照API候補を生成 |
| 関連: 在庫管理 | 在庫確認API候補を生成 |
| 関連: 決済管理 | 決済状態参照・承認注意点を生成 |

### 8.2 MCP設計生成

MCP toolは、AIが扱う業務操作境界としてドメイン別に分ける。

| 分類 | 例 |
|---|---|
| 主ドメインtool | `searchOrders`, `proposeOrderUpdate` |
| 関連ドメインtool | `getProductDetail`, `checkInventoryAvailability` |
| 横断tool | `requestApproval`, `sendNotificationDraft` |

MCP resourceもドメイン別に分ける。

| resource分類 | 例 |
|---|---|
| 主ドメインresource | `orderSummary`, `orderDetail` |
| 関連ドメインresource | `productCatalog`, `inventoryStatus` |
| 横断resource | `approvalPolicy`, `auditLogPolicy` |

### 8.3 Controller雛形生成

Controller雛形では、以下の出力方針にする。

1. 主ドメインControllerを中心に生成する。
2. 関連ドメインControllerは候補として簡略生成する。
3. 横断ドメインは共通ControllerまたはService境界コメントとして扱う。

例:

```text
OrderController
ProductReferenceController
InventoryReferenceController
ApprovalController
```

## 9. Markdown出力影響

Markdown設計書には、以下の章を追加または拡張する。

| 章 | 変更内容 |
|---|---|
| 設計対象概要 | 対象システム名、システム種別、主ドメイン、関連ドメインを表示 |
| API設計サマリー | 主ドメイン中心APIと関連ドメインAPIを分ける |
| RESTエンドポイント一覧 | ドメイン列を追加する |
| MCP tools一覧 | ドメイン列を追加する |
| MCP resources一覧 | ドメイン列を追加する |
| API / MCP tool 対応表 | ドメイン境界を明示する |
| 権限・承認・監査ログ設計 | ドメイン別・横断別に分類する |

### 9.1 出力例


## 12. Codex最小指示方針

後続でCodexに実装させる場合は、最初の指示を小さくする。

### 12.1 初回Codex対象

初回実装対象は以下に限定する。

1. `BlueprintInput` へ `systemName`、`primaryDomain`、`relatedDomains` を追加する。
2. Bean Validationを追加する。
3. 既存 `targetDomain` は削除しない。
4. UI hidden / visible入力の整合を崩さない。
5. 既存テストを通す。

### 12.2 初回Codexで実施しないこと

- Generator全面改修
- Controller雛形生成の全面変更
- MCP tool生成の全面変更
- DB永続化
- 外部LLM連携
- MCPサーバー実装

## 14. 結論

TSK-022では、`targetDomain` をただの複数ドメイン文字列として拡張するのではなく、対象システム名、主ドメイン、関連ドメイン、連携方式、配置方式を分離できる入力モデルへ段階的に移行する。

最初の実装では、互換性維持を優先し、`targetDomain` を残したまま `systemName`、`primaryDomain`、`relatedDomains` を追加する。

Generatorは、主ドメインを中心に詳細設計を生成し、関連ドメインは参照・連携・横断関心として扱う。

これにより、APIM for Spring は単一ドメイン設計支援から、複合業務システムのAPI/MCP設計支援へ拡張できる。
