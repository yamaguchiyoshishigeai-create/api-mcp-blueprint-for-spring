# 待ちフェーズ運用方針

## 1. 目的

本方針は、GitHub Actions等のCI完了待ち、PR mergeability確定待ち、外部処理完了待ちなどの待ちフェーズで、ChatGPTが不要にユーザー指示待ちへ戻らないための運用を定義する。

特に、PRがmerge可能であり、残作業がCI完了待ちのみの場合に、短時間ポーリングを継続せず応答を終了してしまう問題を防止する。

本方針は、既存の `改善タスク課題一覧.md` に記載された「待ちフェーズ運用方針」を補強する具体ルールとして扱う。

## 2. 基本方針

GitHub Actions等のCI完了待ち、PR mergeability確定待ち、外部処理完了待ちなどの待ちフェーズでは、原則としてChatGPTが同一応答ターン内で短時間ポーリングを行う。

短時間ポーリング中は、ユーザーが追加指示、補足、停止、方針変更などのフォローアップ入力を行える前提で扱う。

ポーリング中にユーザーから途中入力があった場合は、直近の自動継続よりユーザー入力を優先し、必要に応じて待ち処理を中断、再確認、または方針変更する。

## 3. ユーザー指示待ちで終了してはならない状態

以下に該当する場合、ChatGPTは原則としてユーザー指示待ちで応答を終了してはならない。

1. PRが `mergeable: true` であり、残作業がCI完了待ちのみの場合。
2. CIの一部jobがsuccessで、一部jobがin_progressの場合。
3. 残り1jobのみin_progressで、失敗がまだ出ていない場合。
4. CI success後のmergeが事前合意済みで、merge前確認だけが残っている場合。
5. merge後の次工程として、ブランチ削除手順提示またはprune確認が残っている場合。

上記の場合は、短時間ポーリングを継続し、success、failure、または明確な長時間化のいずれかが確定するまで確認を続ける。

## 4. CI success時の対応

CIがsuccessになった場合は、事前に合意された範囲で自動的に次工程へ進む。

例:

- squash merge
- 課題管理整理PR作成
- 次PR作成
- リモート作業ブランチ削除手順提示
- `git fetch origin --prune` 確認手順提示
- 次タスク着手可否の判定

## 5. CI failure時の対応

CIがfailureになった場合は、ユーザー指示待ちで終了せず、可能な範囲で以下を確認する。

- 失敗したworkflow
- 失敗したjob
- 失敗したstep
- ログ上の主要エラー
- 原因候補
- 修正方針
- 修正PR更新またはCodex/ChatGPT作業指示の要否

## 6. 長時間化時の一旦報告条件

短時間ポーリングの範囲を明らかに超えて待ち時間が長時間化した場合に限り、一旦報告してよい。

一旦報告する場合は、以下を必ず明示する。

- 未完了状態
- 最終確認時点のPR番号
- commit SHA
- workflow run番号
- 残っているjob名
- 再開時に確認すべきコマンドまたはGitHub確認対象

通常のCI待ち、特に残り1jobのin_progress程度では、原則としてユーザー指示待ちで終了しない。

## 7. バックグラウンド監視の扱い

一度応答を返した後に、ChatGPTがバックグラウンドで常駐監視し、自動的にmergeや修正を実行することは前提にしない。

そのため、同一応答ターン内で確認できる待ちフェーズは、可能な範囲でその場で継続確認する。

## 8. 適用優先度

本方針は、待ちフェーズに関する既存記述の補強として扱う。

既存文書の抽象的な記述と本方針の具体的な終了条件が競合する場合は、本方針の具体条件を優先する。
