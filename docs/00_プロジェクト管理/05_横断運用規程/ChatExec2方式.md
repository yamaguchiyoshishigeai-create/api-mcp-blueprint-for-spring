# ChatExec2方式 運用仕様

## 1. 位置づけ

ChatExec2方式は、従来のChatExec方式を並行作業可能に拡張したローカル実行オフロード方式である。

従来のChatExec方式では、`ChatExec.ps1` / `ChatExec.sh` や `ChatExec.result` のようにスクリプト名・結果ファイル名が固定されるため、複数作業を並行すると結果ファイルの上書き衝突や取り違えが起きやすい。

ChatExec2方式では、作業単位または工程単位で一意な `JOB_ID` を付与し、スクリプト名、実行結果、GitHub投稿内容をその `JOB_ID` に紐づけて管理する。

今後、ユーザーが「ChatExec方式で」と指示した場合は、原則として旧版の固定resultファイル方式ではなく、ChatExec2方式で進める。

ただし、ユーザーが以下のように明示した場合のみ、旧版のChatExec方式を使用する。

- 「旧版のChatExec方式で」
- 「.resultの方で」
- 「ChatExec.result固定の方で」
- その他、旧版・固定resultファイル方式を明示する指示がある場合

## 2. 標準方式

ChatExec2方式の標準案は、GitHub Issue/PRコメント方式とする。

ChatGPTが生成したローカル実行用スクリプトは、実行結果をローカルに生成したうえで、GitHub CLI等を用いて、対象PRコメントまたは専用Issueコメントへ実行結果サマリを投稿する。

ユーザーが「実行完了」と伝えた後、ChatGPTは参照可能なGitHub Issue/PRコメントを読み、`JOB_ID` が一致する結果を確認して次工程を判断する。

## 3. 基本フロー

1. ChatGPTが作業ごとに一意な `JOB_ID` を決める。
   - 例: `C54_STEP1_repo_scan`
2. ChatGPTが `JOB_ID` 付きの単一スクリプトを配布する。
   - 例: `C54_STEP1_repo_scan_R01.cmd`
   - 例: `C54_STEP1_repo_scan_R01.ps1`
   - 例: `C54_STEP1_repo_scan_R01.sh`
3. ユーザーは、マウスクリックまたは単一コマンドでスクリプトを実行する。
4. スクリプトは内部で対象リポジトリへ移動し、必要な確認・編集・テスト等を実行する。
5. スクリプトはローカルに `JOB_ID` 単位の結果を生成する。
6. スクリプトは、GitHub CLI等を使い、対象PRコメントまたは専用Issueコメントへ実行結果サマリを投稿する。
7. ユーザーはチャット上で「実行完了」とだけ伝える。
8. ChatGPTは参照可能なGitHub Issue/PRコメントを読み、`JOB_ID` が一致する結果を確認する。
9. ChatGPTは結果に基づいて次工程を判断する。
10. 必要に応じて、ChatGPTまたは後続スクリプトがコメント削除・クリーンアップを行う。

## 4. Windowsでのエクスプローラー実行UX

Windows環境では、ユーザー操作を最小化するため、エクスプローラー上でダウンロード済みスクリプトをマウスクリックまたはダブルクリックして実行できる運用を重視する。

特に `.cmd` はWindowsでダブルクリック実行されやすいため、Windows向けChatExec2スクリプトでは、必要に応じて `JOB_ID` と配布版識別子を付けた単一 `.cmd` ファイルを配布候補とする。

例:

    C54_STEP1_repo_scan_R01.cmd

ユーザーは、ダウンロード先フォルダをエクスプローラーで開いたまま、対象の `.cmd` ファイルをダブルクリックして実行し、完了後にチャットへ「実行完了」と伝えるだけでよい状態を目指す。

ただし、ダブルクリック実行では処理終了直後にコマンドプロンプトのウィンドウが閉じ、`[OK] ...` / `[FAIL] ...` の最小シグナルをユーザーが確認できない場合がある。

そのため、Windows向け `.cmd` をダブルクリック実行候補として配布する場合は、標準出力に最小シグナルを表示した後、必要に応じて `pause`、`choice`、`timeout`、または `cmd.exe /k` による自己再起動などを用いて、ユーザーが結果を視認できるまでウィンドウを保持する設計を優先する。

このウィンドウ保持は、詳細ログを長く表示するためではなく、成功・失敗の最小シグナルと、必要な場合の次アクションをユーザーが見失わないようにするために行う。

ただし、常駐ターミナルから単一コマンドで実行する用途では、不要なキー入力待ちが再実行性を下げる場合がある。そのため、`.cmd` は可能な範囲で、ダブルクリック実行時はウィンドウ保持、既存ターミナル実行時は過度に邪魔しない挙動を検討する。

配布ファイル数は原則として1ジョブ1ファイルとする。

そのため、`.cmd` と `.ps1` の2ファイルを同時に配布する方式は標準採用しない。PowerShell処理が必要な場合も、可能な範囲で単一 `.cmd` 内からPowerShellを呼び出す、または単一 `.ps1` を提示するなど、ユーザーが迷わない単一ファイル運用を優先する。

## 5. ダウンロードファイル名・再配布・自己参照方針

ChatExec2方式でダウンロードリンクとして配布するスクリプトファイル名は、同一チャット・同一JOBであっても、配布のたびに一意化する。

これは、ブラウザやOSが同名ファイルの再ダウンロード時に ` (1)`、` (2)` などのサフィックスを自動付与し、スクリプト内の固定ファイル名参照や自己再起動処理と不整合を起こすことを防ぐためである。

そのため、ChatGPTが修正版・再配布版・再実行用スクリプトを提示する場合は、`JOB_ID` に加えて配布版識別子を付ける。

例:

    C_TSK030_STEP1_repo_scan_R01.cmd
    C_TSK030_STEP1_repo_scan_R02.cmd
    C_TSK030_STEP1_repo_scan_R03.cmd

`JOB_ID` は作業結果の突合・GitHubコメント検索・後続判断のための論理IDとして維持し、配布版識別子はダウンロードファイル衝突を避けるための物理ファイル名識別子として扱う。

スクリプト内部で自身を再起動する場合、または自身のファイル名・配置場所をログや結果に記録する場合は、ChatGPTが想定した固定ファイル名を使ってはならない。実行中の自分自身の実ファイル名・実パスを参照する。

代表例:

- Windows `.cmd`: `%~f0`、`%~nx0`、`%~dp0`
- PowerShell: `$PSCommandPath`、`$MyInvocation.MyCommand.Path`
- Bash: `$0`、必要に応じて `readlink` 等で解決した実パス

特にWindows `.cmd` でダブルクリック実行時に永続ウィンドウへ自己再起動する場合は、以下のように実ファイルパスを使う。

    start "<JOB_ID>" cmd.exe /k ""%~f0" __run"

この方針により、ユーザーのダウンロード先に `C_TSK030_STEP1_repo_scan_R02.cmd` が保存された場合でも、あるいはOSにより `C_TSK030_STEP1_repo_scan_R02 (1).cmd` として保存された場合でも、スクリプトは実際に起動された自分自身を参照して処理を継続できる。

GitHub Issue/PRコメントやローカル結果には、論理IDとしての `JOB_ID` に加えて、可能な範囲で実行されたスクリプトの実ファイル名も記録する。

## 6. ローカル詳細結果ディレクトリ方針

ChatExec2方式では、ローカル詳細結果を対象リポジトリ配下の `.chatexec2/` ディレクトリへ出力してよい。

`.chatexec2/` は、GitHub Issue/PRコメントへ投稿するサニタイズ済みサマリでは表現しきれない詳細ログ、補助的な調査結果、再現確認用のローカル実行結果を置くためのローカル補助ディレクトリである。

ChatGPTが通常確認すべき正規結果は、GitHub Issue/PRコメントへ投稿されたサニタイズ済みサマリである。`.chatexec2/` 配下の詳細ファイルは、通常フローではChatGPTが直接確認する前提にしない。

`.chatexec2/` 配下のファイルを確認するのは、以下のような例外時に限定する。

- GitHub Issue/PRコメントへの投稿に失敗した場合。
- サニタイズ済みサマリだけでは失敗原因や次工程判断に必要な情報が不足する場合。
- ユーザーが必要部分を確認し、秘密情報や不要な絶対パス等を除去したうえでチャットへ貼り付ける場合。
- ユーザーが明示的に詳細結果ファイルをアップロードする場合。

`.chatexec2/` はGit管理対象外とする。各リポジトリの `.gitignore` には、原則として以下を登録する。

    .chatexec2/

この方針により、ChatExec2のローカル詳細結果がSourcetree等のGUIで未追跡ファイルとして表示され続けること、または誤ってコミットされることを防ぐ。

## 7. GitHubコメントに含める情報

GitHub Issue/PRコメントへ投稿する実行結果には、原則として以下を含める。

- `JOB_ID`
- `STATUS`
- 対象リポジトリ
- 対象ブランチ
- 実行内容の要約
- 変更ファイル一覧
- テスト結果サマリ
- エラー要約
- 次に必要な判断事項
- 実行開始・終了時刻
- スクリプト名

## 8. GitHubコメントに含めてはならない情報

GitHub Issue/PRコメントには、原則として以下を含めない。

- 秘密情報
- トークン
- `.env` の中身
- 秘密鍵
- フル環境変数
- 長大ログ全文
- 個人情報
- 不要な絶対パス
- 認証情報
- 外部非公開情報の過剰な詳細
- 未サニタイズのエラー全文

投稿内容は、ChatGPTが次工程を判断するためのサニタイズ済み要約に限定する。

## 9. 非推奨方式

通常作業ブランチへ `.result` を `commit & push` する方式は、標準採用しない。

理由は以下である。

- Git履歴に `.result` が残る。
- 後で削除しても過去コミットには残る。
- 作業ブランチを汚染する。
- PRに不要な結果ファイルが混入する可能性がある。
- ローカルパス、エラー内容、環境情報等が漏洩する可能性がある。
- 並行作業時にpush競合や取り違えが起きる可能性がある。

## 10. 補助案

以下は標準ではなく、必要時の補助案として扱う。

- Result専用ブランチ方式
- 接続済みDrive同期方式
- ユーザーによるresultファイルアップロード方式
- ユーザーによるresult内容貼り付け方式

## 11. ChatGPT側の案内ルール

ChatGPTがChatExec2方式でスクリプトを提示する場合は、原則として以下を守る。

- 1ジョブにつき単一スクリプトを配布する。
- スクリプト名は `JOB_ID` と配布版識別子を組み合わせて一意化する。
- 同一JOBの修正版・再配布版を提示する場合も、前回と同じダウンロードファイル名を使わない。
- スクリプト内で自身を再起動・参照する場合は、固定ファイル名ではなく実行中の自分自身の実ファイル名・実パスを参照する。
- ユーザーに長いコマンドを毎回コピー＆ペーストさせない。
- ユーザーに不要なファイル移動を要求しない。
- ユーザーに不要な `cd <repo>` を要求しない。
- 対象リポジトリパス、対象ブランチ、Issue/PR番号等の具体値は、可能な限りスクリプト内に埋め込む。
- ユーザーは実行後に「実行完了」と伝えればよい状態を目指す。
- Windows向けスクリプトでは、必要に応じてエクスプローラーからダブルクリック実行しやすい単一 `.cmd` ファイルを配布候補とする。
- Windows向け `.cmd` では、ダブルクリック実行時にウィンドウが即時終了して結果を見失わないよう、必要に応じて終了前のキー入力待ち、短時間待機、または `cmd.exe /k` による永続ウィンドウ化を入れる。
- ローカル詳細結果を出力する場合は、`.chatexec2/` 配下へ出力し、GitHubコメントにはサニタイズ済みサマリのみを投稿する。
- GitHub投稿後、ChatGPTはまずGitHub Issue/PRコメントを確認する。
- 参照できない場合のみ、代替手段を提示する。

## 12. クリーンアップ方針

GitHub Issue/PRコメントには監査ログ・通知・履歴が残る可能性がある。

そのため、必要に応じて以下のいずれかでクリーンアップする。

- ChatGPTが削除可能な場合は、読後にコメントを削除する。
- ChatGPTが削除できない場合は、後続スクリプトで削除する。
- 削除できない場合は、最小限のサマリのみ残す。

ただし、ChatGPTが必ず削除できるとは限らないため、制度上は「ChatGPTまたはスクリプトがクリーンアップする」と扱う。

## 13. 目的

ChatExec2方式の目的は、ローカル実行の安全性を保ちながら、ユーザー操作を最小化し、複数作業の並行実行を可能にすることである。

特に以下を重視する。

- 結果ファイルの上書き衝突を避ける。
- チャットごとの作業結果を取り違えない。
- ユーザーが毎回ファイルをアップロードしなくてよい状態を目指す。
- ChatGPTがGitHub上のIssue/PRコメントから結果を確認できる状態を作る。
- 作業ブランチやGit履歴を不要な `.result` ファイルで汚染しない。
- Windowsでは、ユーザーがエクスプローラー上の単一スクリプトを実行し、完了後に「実行完了」と伝えるだけでよい状態を目指す。
- Windowsダブルクリック実行時でも、ユーザーが成功・失敗の最小シグナルを見失わない状態を目指す。
- 同名ダウンロードによる自動リネームや取り違えを防ぎ、再配布版ごとの実行対象を明確にする。
- `.chatexec2/` のローカル詳細結果をGit管理対象外とし、誤コミットとGUI上の未追跡ノイズを防ぐ。
