# CIポーリング終了条件固定方針

## 1. 目的

本書は、GitHub Actions等のCI待ち、PR mergeability確定待ち、外部処理完了待ちにおいて、ChatGPTが短時間ポーリングをどの時点まで継続し、どの条件で応答を区切ってよいかを明確化するための横断運用規程である。

既存の待ちフェーズ運用では、CI完了待ち等でChatGPTが同一応答ターン内に短時間ポーリングを行う方針を定めている。しかし、`queued` / `in_progress` のまま数回確認しただけで「長引いている」と判断して応答を区切る余地が残っていたため、終了条件を固定する。

## 2. 基本原則

CI、PR mergeability、外部処理等の待ちフェーズでは、`queued` / `in_progress` は終了条件ではない。

ChatGPTは、原則として同一応答ターン内で短時間ポーリングを継続し、以下のいずれかに到達するまで「長引いている」という理由だけで応答を区切ってはならない。

- `success`
- `failure`
- `cancelled`
- `timed_out`
- 明確な取得不能
- ユーザー割り込み
- 異常長時間化

## 3. ポーリング継続条件

以下の状態では、ポーリングを継続する。

| 状態 | 扱い |
|---|---|
| `queued` | 待機中であり、終了条件ではない |
| `in_progress` | 実行中であり、終了条件ではない |
| Job内の一部Stepがsuccess | Job全体が完了するまで継続 |
| 片方のJobのみsuccess | 全Job完了まで継続 |
| Post処理中 | Job全体がcompletedになるまで継続 |

数回確認しても `queued` / `in_progress` のままであることだけを理由に、応答を区切ってはならない。

## 4. ポーリング終了条件

以下のいずれかに到達した場合、ポーリングを終了して状態を報告する。

| 終了条件 | 報告内容 |
|---|---|
| 全Job success | `CI_GREEN` として報告し、次アクション候補を提示する |
| failure | 失敗Job、失敗Step、ログ確認方針、修正方針を提示する |
| cancelled | cancelled状態、再実行可否、次アクションを提示する |
| timed_out | timed_out状態、原因切り分け方針、再実行可否を提示する |
| 取得不能 | APIエラー、レート制限、認証問題、ツール制約等を明示する |
| ユーザー割り込み | 直近のユーザー入力を優先し、ポーリングを中断または方針変更する |
| 異常長時間化 | 最終確認状態、継続困難な理由、再開点を明示する |

## 5. 異常長時間化の扱い

異常長時間化は、単に数回ポーリングしてまだ完了しない状態を意味しない。

異常長時間化として扱ってよいのは、以下のような場合に限定する。

- 同一応答ターン内での継続がツール実行制約上明らかに困難になった場合。
- CI側で通常想定を大きく超える待機・実行時間が発生している場合。
- 外部サービス側の停止、レート制限、認証失効、API応答不安定などにより、完了確認が現実的でない場合。
- ユーザーから別指示、停止、方針変更が入った場合。

異常長時間化として応答を区切る場合でも、以下を必ず明示する。

1. 最終確認したworkflow runまたは対象処理ID。
2. 最終確認時点のJob / Step状態。
3. なぜ継続困難と判断したか。
4. 再開時に確認すべき対象。
5. 未完了状態であり、success扱いではないこと。

## 6. 禁止事項

以下を禁止する。

- `queued` / `in_progress` のみを理由に「長引いている」と判断して応答を区切ること。
- CIが完了していない状態を `CI_GREEN`、`DONE`、`SUCCESS` と扱うこと。
- 一部Jobのみsuccessの状態を全体successとして扱うこと。
- Post処理中のJobを完了扱いすること。
- ポーリングを打ち切ったにもかかわらず、再開点を明示しないこと。
- ユーザー割り込みより直近の自動継続を優先すること。

## 7. CI success後の扱い

全Jobがsuccessになった場合、ChatGPTは `CI_GREEN` として状態を明示する。

その後のmerge、課題管理整理、branch cleanup、横展開は、それぞれ別のアクションとして扱う。

ただし、同一作業内でユーザーが明確にmergeまで委任している場合、ChatGPT(リポジトリ操作)は、PR差分・CI・mergeability・head SHAを確認したうえで、squash mergeへ進めてよい。

この場合も、CI未完了状態から無言でmergeへ進めてはならない。必ずCI successとmergeabilityを確認する。

## 8. 報告フォーマット

CIポーリング中または終了時の報告は、以下の粒度を標準とする。

```text
CI status:
- workflow run: <id>
- checks: <queued | in_progress | success | failure | cancelled | timed_out>
- windows-wrapper-check: <queued | in_progress | success | failure | cancelled | timed_out>
- final status: <CI_WAITING | CI_GREEN | CI_FAILED | CI_BLOCKED>

Next action:
- <merge / failure investigation / rerun / wait continuation / resume target>
```

## 9. 他規程との関係

本方針は、以下の規程を置き換えず、CI待ちフェーズの終了条件を具体化する。

- `00_運用ルール索引と実行ゲート.md`
- `改善タスク課題一覧.md` 内の待ちフェーズ運用方針
- `安全チェック発生時の仕様不変切替方針.md`
- `実行計画と実行指示の分離方針.md`

重複がある場合は、より厳しい終了条件、より明確な未完了扱いを優先する。

## 10. 完了条件

本方針の適用完了条件は以下である。

1. `queued` / `in_progress` が終了条件ではないことが明文化されている。
2. ポーリング継続条件と終了条件が表で整理されている。
3. 異常長時間化の例外条件が限定されている。
4. CI success後の `CI_GREEN` 扱いと、merge等の後続アクションの分離が明文化されている。
5. TSK-048として改善タスク管理に登録されている。
