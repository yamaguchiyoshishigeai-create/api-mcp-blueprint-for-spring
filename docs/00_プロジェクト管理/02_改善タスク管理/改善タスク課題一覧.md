# 改善タスク課題一覧

## ID運用方針

本リポジトリにおける正規タスクIDは `TSK-###` とする。

作業タスク、改善課題、実装指示、レビュー指摘、運用改善、ドキュメント整備の採番には、必ず `TSK-###` を使用する。

`APIM-###` など、プロジェクト名・製品名・機能名・フェーズ名・略称をもとにした独自タスクIDを新設してはならない。

`APIM` はプロジェクト名または説明上の名称としてのみ使用し、課題管理IDとしては使用しない。

## 状態フォルダ保持方針

改善タスク管理の状態フォルダは、現在対象タスクが0件であっても将来利用する前提で保持する。

以下の状態フォルダには .gitkeep を配置し、空フォルダ化によるGit操作時の対話プロンプト発生を防止する。

- 未解決/
- 解決中/
- 確認待ち/
- 保留/
- 解決済み/

## 外部実行結果ファイル方針

PowerShell等の外部実行結果ファイルは、実行対象リポジトリのルートへ `ChatExec.result` または `CodexExec.result` として毎回上書き出力する。

これらの結果ファイルおよび付随する標準出力・標準エラーログは `.gitignore` に登録し、コミット対象にしない。

## Windows Git安定化方針

Windows環境でGit内部メンテナンスによる `.git/objects/*` 削除確認が大量発生する場合は、リポジトリローカル設定として自動GCと自動maintenanceを停止し、必要時のみ手動メンテナンスを行う。

`.git/objects` はGit内部データベースであり、`.gitignore` では制御しない。

## 待ちフェーズ運用方針

GitHub Actions等のCI完了待ち、PR mergeability確定待ち、外部処理完了待ちなどの待ちフェーズでは、原則としてChatGPTが同一応答ターン内で短時間ポーリングを行う。

短時間ポーリング中は、ユーザーが追加指示、補足、停止、方針変更などのフォローアップ入力を行える前提で扱う。

ポーリング中にユーザーから途中入力があった場合は、直近の自動継続よりユーザー入力を優先し、必要に応じて待ち処理を中断、再確認、または方針変更する。

CIがsuccessになった場合は、事前に合意された範囲で自動的に次工程へ進む。例: squash merge、次PR作成、ローカル反映手順提示。

CIがfailureになった場合は、失敗ログ確認、原因切り分け、最小修正方針提示、または修正PR更新へ自動的に進む。

待ち時間が長時間化した場合は、未完了状態、最終確認時刻相当の状態、再開時に確認すべきコマンドまたはPR番号を明示して一旦報告する。

一度応答を返した後にバックグラウンドで常駐監視し、自動的にmergeや修正を実行することは前提にしない。

## squash merge後ブランチ整理方針

PRをsquash mergeした後は、作業ブランチを削除対象とする。

GitHubコネクタの `merge_pull_request` でmergeした場合、`gh pr merge --delete-branch` と異なり作業ブランチ削除は自動実行されないため、merge後に別途リモート作業ブランチ削除を行う。

ローカル環境では、リモート作業ブランチ削除後に `git fetch origin --prune` を実行し、削除済みリモート追跡参照を整理する。

Sourcetree等のGUIで、squash merge済みの作業ブランチがmainへ合流していないように見える場合は、まずmain上に成果物が反映済みかを確認し、次に残存リモート作業ブランチとローカルリモート追跡参照を確認する。

squash mergeでは作業ブランチ上の個別コミットIDはmainの祖先にならないため、グラフ上の枝残りだけで未統合とは判断しない。
