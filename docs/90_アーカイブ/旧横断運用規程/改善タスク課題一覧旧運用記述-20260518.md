```text
## 外部実行結果ファイル方針

PowerShell等の外部実行結果ファイルは、実行対象リポジトリのルートへ `ChatExec.result` または `CodexExec.result` として毎回上書き出力する。

これらの結果ファイルおよび付随する標準出力・標準エラーログは `.gitignore` に登録し、コミット対象にしない。

## Windows Git安定化方針

Windows環境でGit内部メンテナンスによる `.git/objects/*` 削除確認が大量発生する場合は、リポジトリローカル設定として自動GCと自動maintenanceを停止し、必要時のみ手動メンテナンスを行う。

`.git/objects` はGit内部データベースであり、`.gitignore` では制御しない。

## 待ちフェーズ運用方針

GitHub Actions等のCI完了待ち、PR mergeability確定待ち、外部処理完了待ちなどの待ちフェーズでは、原則としてChatGPTが同一応答ターン内で短時間ポーリングを行う。

短時間ポーリング中は、ユーザーが追加指示、補足、停止、方針変更などのフォローアップ入力を行える前提で扱う。

ポーリング中にユーザーから途中入力があった場合は、直近の自動継続よりユーザー入力を優先し、必要に応じて待ち処理を中断、再確認、または方針変更する。

CIがsuccessになった場合は、事前に合意された範囲で自動的に次工程へ進む。例: squash merge、次PR作成、ローカル反映手順提示。

CIがfailureになった場合は、失敗ログ確認、原因切り分け、最小修正方針提示、または修正PR更新へ自動的に進む。

待ち時間が長時間化した場合は、未完了状態、最終確認時刻相当の状態、再開時に確認すべきコマンドまたはPR番号を明示して一旦報告する。

一度応答を返した後にバックグラウンドで常駐監視し、自動的にmergeや修正を実行することは前提にしない。

## squash merge後ブランチ整理方針

PRをsquash mergeした後は、作業ブランチを削除対象とする。

GitHubコネクタの `merge_pull_request` でmergeした場合、`gh pr merge --delete-branch` と異なり作業ブランチ削除は自動実行されないため、merge後に別途リモート作業ブランチ削除を行う。

ローカル環境では、リモート作業ブランチ削除後に `git fetch origin --prune` を実行し、削除済みリモート追跡参照を整理する。

Sourcetree等のGUIで、squash merge済みの作業ブランチがmainへ合流していないように見える場合は、まずmain上に成果物が反映済みかを確認し、次に残存リモート作業ブランチとローカルリモート追跡参照を確認する。

squash mergeでは作業ブランチ上の個別コミットIDはmainの祖先にならないため、グラフ上の枝残りだけで未統合とは判断しない。

## 順次タスクmergeゲート方針

前タスクがmainへmergeされる前に後続タスクへ着手すると、タスク起点、PR状態、課題管理状態が不整合になるリスクがある。

この問題を防止するため、次の正規TSKへ着手する前に、直前タスクについて以下を完了していなければならない。

1. 実装PRまたはdocs PRのCIがsuccessであること。
2. 当該PRがmainへmerge済みであること。
3. 課題管理整理PRが必要な場合は、そのPRもCI success確認後にmainへmerge済みであること。
4. merge後のリモート作業ブランチが削除済みであること。
5. ローカル環境で `git fetch origin --prune` が実行済みであること。
6. `git branch -r` で当該作業ブランチが残っていないことを確認済みであること。

上記が完了するまで、次の正規TSKのブランチ作成、実装、PR作成へ進んではならない。

例外として、緊急修正や同一障害の復旧作業など、直前タスクを完了させるために必要な作業は許容する。その場合も、新規TSKとして独立進行しているように見えるブランチ名・PR名を避け、直前タスクの復旧・修正であることを明記する。

この方針は、TSK-025、TSK-026、TSK-027で試行し、前タスク未merge状態で後続タスクへ進む問題を防止できたため、有用性確認済みとして標準運用に組み込む。

## ChatExec2方式方針

ローカル実行を伴う作業では、並行作業対応版として `ChatExec2方式` を標準候補とする。

ユーザーが「ChatExec方式で」と指示した場合は、原則として旧版の固定 `ChatExec.result` 方式ではなく、作業単位・工程単位で一意な `JOB_ID` を付与するChatExec2方式で進める。

旧版のChatExec方式は、ユーザーが「旧版のChatExec方式で」「.resultの方で」「ChatExec.result固定の方で」など、固定resultファイル方式を明示した場合のみ使用する。

ChatExec2方式でダウンロードリンクとして配布するスクリプトファイル名は、同一JOBであっても再配布のたびに `R01`、`R02`、`R03` などの配布版識別子を付けて一意化する。

スクリプト内部で自身を再起動・参照する場合は、固定ファイル名ではなく、実行中の自分自身の実ファイル名・実パスを参照する。

`.chatexec2/` はChatExec2のローカル詳細結果ディレクトリであり、GitHub Issue/PRコメントのサニタイズ済みサマリでは不足する場合の補助ログ置き場として扱う。通常確認先はGitHub Issue/PRコメントであり、`.chatexec2/` はGit管理対象外とする。

ChatExec2方式の詳細は `docs/00_プロジェクト管理/05_横断運用規程/ChatExec2方式.md` を正とする。

## AI作業分担方針

実装支援AIの利用が推奨されるタスクであっても、いきなり実装支援AIへ丸投げせず、まずChatGPT(会話内)またはChatGPT(リポジトリ編集)による実装境界定義、スコープ分割、docs・課題管理整備、実装支援AI向け指示書作成を優先検討する。

Codexは現時点で標準的に利用する実装支援AIの代表例として扱う。ただし、将来的にGemini、GitHub Copilot、その他の実装支援AIを併用または置き換え利用する場合にも同じ分担方針を適用する。

AI作業分担方針の詳細は `docs/00_プロジェクト管理/05_横断運用規程/AI作業分担方針.md` を正とする。
```
